# 1、上位机的数据用哪个串口接收？用的什么方式？

- **使用的串口：** 项目中采用的是 **UART1** 串口。根据代码目录结构中 `comm_task.c` 的注释说明，该串口专门用于承载下位机与上位机（如 Jetson 设备）之间的通信。
    
- **采用的接收方式：** 采用的是 **`UART DMA 接收` + `空闲中断（IDLE Interrupt）`** 的组合方式，并且配合了 FreeRTOS 的**流缓冲区（StreamBuffer）**。

### ⚙️ 这种接收方式是如何工作的？（工作时序）

1. **底层的搬运（UART DMA 环形模式）：** 当上位机发来数据时，不需要 CPU 频繁介入，底层硬件 **DMA（直接内存访问）** 会以环形缓冲区（Ring Buffer）的模式，自动把串口接收到的原始字节流搬运到指定的内存中。
    
2. **断帧与触发（空闲中断 ISR）：** 当一帧数据发送完毕，串口线上出现超过 1 个字节时间的空闲时，单片机就会触发**串口空闲中断（IDLE）**。在中断服务函数（ISR）中，系统会计算当前接收到了多少新字节。
    
3. **安全推入（StreamBuffer）：** 在空闲中断中，调用 `StreamBufferSendFromISR()` 函数，将新收到的这批数据迅速推入 FreeRTOS 的流缓冲区（StreamBuffer）中。
    
4. **任务阻塞与解析（CommTask）：** 而我们的 **`CommTask`（通信任务）** 平时处于阻塞等待状态。一旦流缓冲区有了数据，它就会被唤醒，并从流缓冲区中**逐字节读取**数据，通过**状态机**去匹配帧头、消息 ID、进行 CRC 校验。
    
5. **业务通知（Task Notification）：** 一旦状态机确认解析出了一帧完整且合法的有效速度指令（如 `CmdVel`），它会更新全局最新命令，并最终通过 **任务通知（Task Notification）** 去唤醒高优先级的 `ControlTask`（控制任务）来进行真正的电机闭环控制。
    

### 💡 这样设计在面试中的闪光点（为什么好？）

在校招面试中，如果被问到串口接收，您可以重点强调这个设计的精妙之处：

> “我们没有采用传统的『每收到一个字节就进一次中断』的方式，因为高频的字节中断会严重压榨 CPU。我们采用 **DMA 环形接收配合空闲中断**，只有在『一帧数据收完』的空闲节点才进一次中断，然后通过 **StreamBuffer** 实现中断与任务之间的解耦。这极大降低了 CPU 负荷，保证了控制系统整体的实时性。”


# 3、通信用的协议帧数据格式是怎样的？
根据目前文档页面中提取到的大纲信息，虽然暂时无法看到 **3.4.1 协议帧格式** 具体的逐字节定义（比如具体的帧头长什么样），但我们可以从它包含的几个子小节和解析机制中，推断出这个通信协议帧的几个**核心要素**：

结合大纲中的 **“3.4.1.1 大端与小端”**、**“3.4.1.2 CRC校验”** 以及 **“3.4.4 状态机逐字节解析”**，一个标准的上下位机通信协议帧通常包含以下结构设计：

### 1. 标准的数据帧结构（推断）

为了能让 `CommTask` 使用**状态机逐字节解析**，协议帧必然有严格的先后顺序，通常长这样：

- **帧头（Header/Sync）**：比如固定的 `0x5A 0xA5`，用于状态机第一时间识别一帧数据的开始。
    
- **指令类型（Command ID）**：标识这帧数据是做什么的，比如“速度下发（`cmd_vel`）”还是“心跳包”。
    
- **数据长度（Length）**：指明后面跟着多少个字节的有效数据，防止发生数组越界。
    
- **有效载荷（Payload / Data）**：真正要传输的核心数据，比如机器人的线速度和角速度。
    
- **校验尾（CRC Checksum）**：文档明确提到了 **CRC校验**。放在帧的末尾，用来验证整包数据在传输过程中有没有发生位翻转或丢失。如果 CRC 算出来对不上，这帧数据就会被直接丢弃（Invalid Frame）。
    

### 2. 关键的技术细节

- **大端与小端（Endianness）**：由于有效载荷中传递的速度（`cmd_vel`）通常是多字节数据（如 16 位整型或 32 位浮点数 `float`），而不同架构的芯片（比如 ARM 的 STM32 和 ARM/x86 的 Jetson）可能存在字节序差异。协议帧必须明确规定先发高字节还是低字节，否则解出来的速度值会是个错乱的天文数字。
    
- **内存对齐（Memory Alignment）**：大纲在 **3.4.5.3 内存对齐** 中也提到了这一点。在把接收到的字节流强转为结构体时，需要考虑单片机内存地址对齐的问题，通常会使用 `#pragma pack(1)` 来让结构体紧凑排列，与协议帧完全对应。
    

建议您在文档左侧目录点击 **3.4.1 协议帧格式** 展开正文，就可以看到具体的字节数和帧头定义啦！

您是比较好奇这个帧里头“具体包了哪些数据”，还是想了解一下它是怎么用“状态机”把这串数据一节一节抠出来的呢？

SOF1 | SOF2 | VER | MSG_ID | FLAGS | SEQ | LEN | PAYLOAD | CRC16 | EOF0 | EOF1  帧头 + 描述信息 + 实际数据 + 校验码 + 帧尾

|字段|字节数|数据类型|示例值|说明|
|---|--:|---|---|---|
|SOF1|1|uint8|0xAA|帧头第 1 字节，表示一帧开始|
|SOF2|1|uint8|0x55|帧头第 2 字节，和 SOF1 组合确认帧起始|
|VER|1|uint8|0x00|协议版本号|
|MSG_ID|1|uint8|0x01|消息类型 ID，表示当前帧用途|
|FLAGS|1|uint8|0x00|标志位，预留扩展|
|SEQ|1|uint8|0x00|序列号，预留字段|
|LEN|2|uint16，小端|0x06 00|Payload 长度，单位字节|
|PAYLOAD|LEN|byte[]|—|实际有效数据|
|CRC16|2|uint16，小端|—|CRC-16 校验值|
|EOF0|1|uint8|0x66|帧尾 0|
|EOF1|1|uint8|0xBB|帧尾 1|
一帧的典型结构可以写成
```c
[0xAA][0x55][VER][MSG_ID][FLAGS][SEQ][LEN_L][LEN_H][PAYLOAD...][CRC_L][CRC_H][0x66][0xBB]
```

# 4、代码里面如何解析数据帧？

代码里面是用**状态机逐字节解析数据帧**的，不是一次性把一整帧读出来再解析。

核心流程是：

```text
UART DMA接收 -> 空闲中断判断收到一段新数据 -> 写入StreamBuffer
-> CommTask从StreamBuffer读取字节块
-> 对每个字节调用 parser_feed_byte(b)
-> 状态机按字段推进
-> CRC校验通过后调用 on_valid_frame()
```

文档里的状态机解析顺序是：

```text
WAIT_SOF1 -> WAIT_SOF2 -> VER -> MSG_ID -> FLAGS -> SEQ
-> LEN0 -> LEN1 -> PAYLOAD -> CRC0 -> CRC1 -> reset
```

对应协议帧：

```text
AA 55 | VER | MSG_ID | FLAGS | SEQ | LEN_L LEN_H | PAYLOAD... | CRC_L CRC_H | 66 BB
```

其中代码主要靠 `parser_feed_byte(uint8_t b)` 每次处理 1 个字节。它根据当前状态判断这个字节应该属于哪个字段，并决定是否进入下一个状态。文档第 1 页的 **3.4.4 状态机逐字节解析** 和 **3.4.4.2 逐字节解析** 部分就是这个逻辑。

示例代码结构可以写成这样：

```c
typedef enum {
    ST_WAIT_SOF1 = 0,
    ST_WAIT_SOF2,
    ST_VER,
    ST_MSG_ID,
    ST_FLAGS,
    ST_SEQ,
    ST_LEN0,
    ST_LEN1,
    ST_PAYLOAD,
    ST_CRC0,
    ST_CRC1,
} ParseState_t;

static ParseState_t s_state = ST_WAIT_SOF1;

static uint8_t  s_ver;
static uint8_t  s_msg_id;
static uint8_t  s_flags;
static uint8_t  s_seq;
static uint16_t s_len;
static uint8_t  s_payload[MAX_PAYLOAD_LEN];
static uint16_t s_payload_idx;
static uint16_t s_crc;
static uint8_t  s_crc_lo;
```

解析函数的核心逻辑是：

```c
static void parser_feed_byte(uint8_t b)
{
    switch (s_state) {
    case ST_WAIT_SOF1:
        if (b == 0xAA) {
            s_state = ST_WAIT_SOF2;
        }
        break;

    case ST_WAIT_SOF2:
        if (b == 0x55) {
            s_crc = 0xFFFF;          // CRC 从 VER 开始算
            s_state = ST_VER;
        } else if (b == 0xAA) {
            s_state = ST_WAIT_SOF2;  // 处理 AA AA 55 这种重叠帧头
        } else {
            s_state = ST_WAIT_SOF1;
        }
        break;

    case ST_VER:
        s_ver = b;
        s_crc = crc16_ccitt_update(s_crc, b);
        s_state = ST_MSG_ID;
        break;

    case ST_MSG_ID:
        s_msg_id = b;
        s_crc = crc16_ccitt_update(s_crc, b);
        s_state = ST_FLAGS;
        break;

    case ST_FLAGS:
        s_flags = b;
        s_crc = crc16_ccitt_update(s_crc, b);
        s_state = ST_SEQ;
        break;

    case ST_SEQ:
        s_seq = b;
        s_crc = crc16_ccitt_update(s_crc, b);
        s_state = ST_LEN0;
        break;

    case ST_LEN0:
        s_len = b;                   // 小端：低字节
        s_crc = crc16_ccitt_update(s_crc, b);
        s_state = ST_LEN1;
        break;

    case ST_LEN1:
        s_len |= ((uint16_t)b << 8);  // 小端：高字节
        s_crc = crc16_ccitt_update(s_crc, b);

        if (s_len > MAX_PAYLOAD_LEN) {
            parser_reset();          // 长度异常，丢弃本帧
        } else if (s_len == 0) {
            s_state = ST_CRC0;
        } else {
            s_payload_idx = 0;
            s_state = ST_PAYLOAD;
        }
        break;

    case ST_PAYLOAD:
        s_payload[s_payload_idx++] = b;
        s_crc = crc16_ccitt_update(s_crc, b);

        if (s_payload_idx >= s_len) {
            s_state = ST_CRC0;
        }
        break;

    case ST_CRC0:
        s_crc_lo = b;                // CRC 小端低字节
        s_state = ST_CRC1;
        break;

    case ST_CRC1: {
        uint16_t rx_crc = (uint16_t)s_crc_lo | ((uint16_t)b << 8);

        if (rx_crc == s_crc) {
            on_valid_frame();        // 校验通过，处理有效帧
        }

        parser_reset();              // 无论成功失败，都回到找帧头
        break;
    }

    default:
        parser_reset();
        break;
    }
}
```

有效帧处理时，再根据 `MSG_ID` 解释 `PAYLOAD`。例如 `CMD_VEL` 速度控制帧的 payload 是 6 字节，按 3 个小端 `int16_t` 解析：

```c
static void on_valid_frame(void)
{
    if (s_ver != 0x00) return;
    if (s_msg_id != 0x01) return;    // CMD_VEL
    if (s_flags != 0x00) return;
    if (s_len != 6) return;

    int16_t vx = (int16_t)(s_payload[0] | (s_payload[1] << 8));
    int16_t vy = (int16_t)(s_payload[2] | (s_payload[3] << 8));
    int16_t wz = (int16_t)(s_payload[4] | (s_payload[5] << 8));

    // 更新全局速度命令，必要时进入临界区保护
    g_cmd_vx_mmps   = vx;
    g_cmd_vy_mmps   = vy;
    g_cmd_wz_mradps = wz;

    // 通知 ControlTask 有新命令
    xTaskNotifyGive(controlTaskHandle);
}
```

关键点可以概括为三句话：

1. **不是按包解析，而是按字节喂给状态机。** 串口数据可能分段、粘包、错位，所以每个字节都要能推进或恢复同步。
    
2. **CRC 从 `VER` 开始算，到 `PAYLOAD` 结束，不包含帧头、CRC 字段和帧尾。**
    
3. **收到 `CRC1` 后比较接收 CRC 和本地计算 CRC；一致才认为是有效帧，否则丢弃并回到等待帧头。**

# 5、接4，为什么用这种方式解析数据帧?
