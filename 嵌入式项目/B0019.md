# 16、项目中为啥要把日志单独做成任务，而不是用printf

项目中把日志单独做成 **LogTask**，而不是在各个任务里直接 `printf`，核心原因是：**避免日志打印影响实时控制任务**。

可以这样理解：

```text
不推荐：
ControlTask / CommTask / SensorTask 里直接 printf

推荐：
各任务把日志消息丢进队列
  ↓
LogTask 统一取出
  ↓
LogTask 统一串口打印
```

### 1. `printf` 是阻塞的，会拖慢实时任务

`printf` 看起来只是打印一句话，但底层通常要经过：

```text
格式化字符串
  ↓
拷贝到缓冲区
  ↓
通过串口逐字节发送
```

串口发送速度很慢，比如 115200 波特率下，打印一长串日志可能占用几毫秒甚至更久。

但控制任务是 **10ms 周期**运行的，如果在 ControlTask 里直接 `printf`，就可能导致：

```text
PID 计算被拖慢
控制周期抖动
PWM 更新不及时
电机控制不稳定
```

所以实时任务里不能随便阻塞打印。你上传的文档里，ControlTask 是周期控制任务，通信、控制、传感器、看门狗等任务都有明确分工；这类结构下，日志打印应该和控制逻辑解耦。

### 2. 多个任务同时 `printf`，输出容易乱

如果多个任务都直接打印：

```c
printf("control speed = ...");
printf("comm recv frame = ...");
printf("sensor value = ...");
```

可能会出现这种情况：

```text
[Control] speed=[Comm] recv AA 55...
```

也就是不同任务的输出互相插入，日志变得很难看懂。

单独用 LogTask 后，所有日志统一排队、统一输出，串口打印就变成串行执行，不容易乱。

### 3. 日志任务可以降低优先级，避免抢占关键任务

控制任务、通信任务、传感器任务通常更重要：

```text
ControlTask：保证电机控制实时性
CommTask：保证通信数据及时解析
SensorTask：保证传感器数据采集
LogTask：只是辅助调试
```

所以 LogTask 可以设置成较低优先级。  
系统忙的时候，先保证控制和通信，日志可以晚一点打印，甚至丢掉一部分调试日志。

如果直接 `printf`，日志打印就发生在当前任务上下文里，哪个任务调用 `printf`，哪个任务就被拖住。

### 4. LogTask 可以用队列做缓冲

推荐结构是：

```text
任务A / 任务B / 中断
  ↓
xQueueSend / xStreamBufferSend
  ↓
LogTask
  ↓
UART 输出
```

各个任务只需要快速把日志放进队列：

```c
Log_Info("vx=%d, wz=%d", vx, wz);
```

真正耗时的串口发送交给 LogTask：

```c
while (1) {
    xQueueReceive(logQueue, &msg, portMAX_DELAY);
    uart_send(msg);
}
```

这样对业务任务的影响很小。

### 5. 方便统一管理日志等级和开关

单独做 LogTask 后，可以统一支持：

```text
ERROR / WARN / INFO / DEBUG
```

也可以根据需要关闭低等级日志：

```c
#define LOG_LEVEL LOG_WARN
```

这样调试时开详细日志，正式运行时只保留错误日志。

如果到处写 `printf`，后期要关日志、改格式、加时间戳、改输出口都会很麻烦。

### 6. 避免影响中断和任务调度

有些 `printf` 实现不是线程安全的，多个任务同时调用可能会有重入问题。  
如果在中断里打印，更容易造成严重问题：

```text
中断执行时间变长
任务调度被延迟
串口发送阻塞
系统实时性下降
```

而 LogTask 的方式是：中断或任务只发送一个简短日志事件，不直接打印。

一句话总结：

**项目中把日志单独做成任务，是为了把耗时、不确定、容易阻塞的串口打印从控制任务和通信任务中剥离出来；各任务只负责投递日志，LogTask 低优先级统一输出，从而保证控制周期稳定、日志不乱、系统实时性更好。**

# 17、LogTask的输入来源是什么？（队列？缓冲区？）

LogTask 的**输入来源是队列，不是环形缓冲区**。

更准确地说：

```text
其他任务 / 中断
  ↓
调用 Log_Post(...)
  ↓
生成 LogRec_t 日志记录
  ↓
xQueueSend() 写入日志队列
  ↓
App_LogTask 用 xQueueReceive() 从队列取出
  ↓
format_line() 格式化成字符串
  ↓
写入 RingBuffer 环形缓冲区
  ↓
UART DMA 发送出去
```

所以可以区分为：

|位置|作用|是输入还是输出|
|---|---|---|
|`Queue` / `logQueue`|保存待处理的日志记录 `LogRec_t`|**LogTask 的输入来源**|
|`RingBuffer`|保存已经格式化好的字符串，等待 UART DMA 发送|**LogTask 的输出缓存**|
|UART DMA|真正把日志通过串口发出去|输出通道|

文档 3.9.2 中写到，日志任务 `App_LogTask` 负责**从队列取出 `LogRec_t`**，再把它格式化成字符串并写入环形缓冲区；主循环中通过 `xQueueReceive()` 阻塞等待新的日志记录，之后调用 `format_line()`，再通过 `rb_write_locked()` 写入 RingBuffer，最后触发 `try_start_dma_locked()` 启动或继续 DMA 发送。

代码逻辑可以理解成这样：

```c
void Log_Post(LogLevel_t lvl, const char *tag, const char *fmt, ...)
{
    LogRec_t rec;

    rec.level = lvl;
    rec.tag = tag;
    rec.fmt = fmt;
    // 保存参数、时间戳等

    xQueueSend(g_logQueue, &rec, 0);
}
```

LogTask 里：

```c
void App_LogTask(void *arg)
{
    LogRec_t rec;
    char line[LOG_LINE_MAX];

    for (;;) {
        xQueueReceive(g_logQueue, &rec, portMAX_DELAY);

        int len = format_line(&rec, line, sizeof(line));

        if (len > 0) {
            rb_write_locked(&g_logRingBuf, line, len);
            try_start_dma_locked();
        }
    }
}
```

一句话总结：

**LogTask 的输入是日志队列 `Queue`，队列里放的是结构化日志记录 `LogRec_t`；环形缓冲区不是输入源，而是 LogTask 格式化日志后用于 UART DMA 异步发送的输出缓存。**

# 18、日志等级是如何设计的？不同等级的作用是什么？

日志等级是按**重要程度从低到高**设计的，常见顺序是：

```text
DEBUG < INFO < WARNING < ERROR
```

文档 3.9.1 里也说明，日志系统会按重要程度分级，例如 `DEBUG、INFO、WARNING、ERROR`，这样可以在不同场景下只输出需要关注的日志，减少干扰。LogTask 收到 `LogRec_t` 后，会格式化成类似 `[INFO][123456][TAG] ...` 的形式再输出。

### 1. `DEBUG`：调试细节日志

`DEBUG` 是最低等级，主要用于开发阶段排查问题。

一般打印：

```text
变量值
状态机状态
函数执行路径
中间计算结果
收发数据细节
```

例如：

```c
LOG_DEBUG("COMM", "state=%d, byte=0x%02X", state, b);
```

作用是帮助开发者看清程序内部执行过程。  
但这类日志数量通常很多，正式运行时一般会关闭。

### 2. `INFO`：正常运行信息

`INFO` 表示系统正常运行过程中的关键状态。

一般打印：

```text
系统启动
任务创建成功
进入某个模式
收到有效命令
参数配置成功
```

例如：

```c
LOG_INFO("CTRL", "enter CTRL_RUN, vx=%d, wz=%d", vx, wz);
```

作用是让开发者知道系统当前在正常工作，以及关键流程走到了哪里。

### 3. `WARNING`：警告信息

`WARNING` 表示出现了异常情况，但系统还能继续运行。

例如：

```text
收到未知命令
数据长度异常
指令接近超时
队列快满
传感器数据偶尔无效
```

示例：

```c
LOG_WARN("COMM", "unknown msg id=%d", msg_id);
```

它的作用是提醒开发者：系统还没崩，但这里可能有风险，需要关注。

### 4. `ERROR`：错误信息

`ERROR` 表示出现比较严重的问题，某个功能已经失败，或者系统需要进入保护处理。

例如：

```text
CRC 连续错误
UART 发送失败
电机驱动异常
编码器长时间无反馈
队列创建失败
内存不足
```

示例：

```c
LOG_ERROR("MOTOR", "encoder timeout");
```

这类日志在正式运行时也应该保留，因为它直接关系到故障定位和系统安全。

### 5. 等级过滤机制

日志等级的核心作用是**过滤日志**。通常代码里会设置一个当前输出等级，比如：

```c
#define LOG_LEVEL_CURRENT LOG_LEVEL_INFO
```

然后判断：

```c
if (level < LOG_LEVEL_CURRENT) {
    return;   // 低等级日志不入队，不输出
}
```

如果当前等级是 `INFO`，那么：

```text
DEBUG   不输出
INFO    输出
WARNING 输出
ERROR   输出
```

如果定位问题时把等级改成 `DEBUG`，就可以看到更详细的调试信息。

### 6. 不同阶段怎么用？

开发调试阶段：

```text
DEBUG + INFO + WARNING + ERROR
```

联调测试阶段：

```text
INFO + WARNING + ERROR
```

正式运行阶段：

```text
WARNING + ERROR
```

故障排查阶段可以临时打开 `DEBUG`，问题定位完成后再关掉，避免日志太多影响系统实时性。

一句话总结：

**日志等级就是给日志按重要程度分层：`DEBUG` 看细节，`INFO` 看正常流程，`WARNING` 看可恢复异常，`ERROR` 看严重错误；通过等级过滤，可以在调试时输出详细信息，在正式运行时只保留关键问题日志。**
