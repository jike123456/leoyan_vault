# 1、项目的目录层级是咋样的？
```c
kaoya_project/ 
 ├─ kaoya_project.ioc       # CubeMX 工程配置文件 
 ├─ .mxproject              # CubeMX/IDE 工程元信息（一般无需关心） 
 │
 ├─ 📁App/                  # 应用层 
 │  ├─ Inc/                 # 应用层头文件 
 │  │  ├─ app_init.h        # App_Init() 声明 
 │  │  ├─ comm_task.h       # 通信任务 
 │  │  ├─ control_task.h    # 控制任务 
 │  │  ├─ log_task.h        # 日志任务 
 │  │  ├─ monitor_task.h    # 监控任务 
 │  │  ├─ iwdg_task.h       # 看门狗任务 
 │  │  ├─ uplink_task.h     # 上行任务：周期性给上位机回传状态 
 │  │  ├─ sensor_task.h     # 传感器任务：电池/IMU/光敏等采集入口 
 │  │  ├─ lcd_task.h        # LCD 显示任务：刷新 UI/状态展示 
 │  │  ├─ led_task.h        # LED 任务 
 │  │ 
 │  └─📁 Src/               # 应用层源文件（每个 task 对应一个 .c） 
 │     ├─ app_init.c        # App_Init(): 系统应用模块初始化 
 │     ├─ comm_task.c       # UART1 
 │     ├─ control_task.c    # 读 cmd_vel -> 逆解 -> PID -> PWM/方向控制 
 │     ├─ log_task.c        # 日志输出线程 
 │     ├─ monitor_task.c    # heap/stack 统计 
 │     ├─ iwdg_task.c       # IWDG 喂狗节拍 + “异常时不喂狗”策略 
 │     ├─ uplink_task.c     # 上位机回传帧组包/发送 
 │     ├─ sensor_task.c     # ADC/I2C/IMU 等采样逻辑 
 │     ├─ lcd_task.c        # LCD 界面刷新 
 │     ├─ led_task.c        # LED 闪烁策略 
 │     └─ power_task.c      # 电源状态机 
 │
 ├─ 📁Bsp/                  # 板级支持包（驱动抽象层） 
 │  ├─ Inc/                 # BSP 头文件 
 │  │  ├─ bsp_usart.h       # 串口底层封装（DMA/发送/接收辅助） 
 │  │  ├─ bsp_log.h         # 日志底层（可能含 DMA 环形缓冲/打印接口） 
 │  │  ├─ protocol.h        # 通信协议定义 
 │  │  ├─ comm_parser.h     # 通信解析状态机 
 │  │  ├─ uplink_proto.h    # 上行协议组包：把状态数据打包成“上位机帧” 
 │  │  ├─ motor.h           # 电机驱动封装：PWM/方向控制接口 
 │  │  ├─ pid.h             # PID 控制器实现
```

1. 工程配置层（根目录）
kaoya_project.ioc：这是 STM32CubeMX 的工程配置文件。在实际开发中，开发者会用 CubeMX 的图形化界面来配置单片机的引脚、时钟树和外设（如 UART、SPI 等），这个文件保存了所有的配置信息。

.mxproject：IDE 或 CubeMX 自动生成的元数据文件，开发时通常不需要去关心或修改它。

2. App 应用层（核心业务逻辑）
App/ 文件夹是整个项目的灵魂所在，包含了所有的上层业务逻辑。它被严格按照功能划分为了多个“任务（Task）”，这正是 FreeRTOS 这种实时操作系统的典型开发模式。

为了保持代码整洁，它分为了 Inc/（存放 .h 头文件，用于声明） 和 Src/（存放 .c 源文件，用于具体实现）。
我们可以把这些任务分为几大类来理解：

系统与初始化

app_init：负责在 RTOS 调度器启动前，把所有的应用模块、任务、队列、信号量等进行统一初始化。

通信与交互（上下位机协同）

comm_task：通信任务，主要负责接收上位机（比如 Jetson 这种大脑）发来的指令进行解析。

uplink_task：上行任务，负责把下位机（STM32）当前的状态（比如速度、电量）打包成协议帧回传给上位机。

运动控制（机器人的小脑）

control_task：控制任务，非常核心！它负责读取上位机下发的目标速度，进行运动学逆解，然后通过 PID 算法计算出需要的 PWM 值去控制电机。

环境感知与反馈

sensor_task：传感器任务，负责汇总采集底层的硬件数据，比如电池电压、IMU（惯性导航）、光敏传感器等。

lcd_task & led_task：人机交互，负责刷新 LCD 屏幕上的 UI 和状态，以及控制 LED 闪烁来提示当前系统运行状态。

系统监控与调试（工程化保障）

log_task：独立出一个线程专门处理日志打印，避免在各个任务里直接调用 printf 导致系统实时性变差或死锁。

monitor_task：监控任务，用来统计系统的内存（heap/stack）使用情况，防止内存泄漏或栈溢出。

iwdg_task：看门狗任务，负责定期“喂狗”，如果系统某个任务卡死，看门狗会触发单片机重启，保证系统具备自恢复能力

### 3. BSP 板级支持包（截图未完全展示，结合大纲理解）

在 `App/` 下方，还有一个 **`Bsp/`（Board Support Package）** 目录。 如果说 `App` 是“想做什么”，那么 `Bsp` 就是“具体怎么驱动硬件去做”。它对底层的硬件（如串口 DMA、电机 PWM 控制器、传感器 I2C 总线等）进行了二次封装，提供给 `App` 层调用

### 4. Core 层（系统核心与硬件初始化）

这个目录下的代码通常是由 **STM32CubeMX 工具自动生成**的，主要负责单片机最基础的“起步”配置。

- **`main.c / main.h`**：程序的绝对主入口。它负责按顺序调用各个底层外设的初始化，最后拉起 FreeRTOS 调度器（RTOS 启动后，控制权就交给 `App` 层的各个任务了）。
    
- **`freertos.c`**：CubeMX 自动生成的 RTOS 初始化文件。项目中所有的 RTOS 任务创建、系统钩子函数（比如涉及到 Tickless 低功耗模式的回调）通常会放在这里。
    
- **`stm32f4xx_it.c`**：非常关键！这是**系统中断服务函数的集中地**。无论是底层的串口接收中断，还是定时器溢出中断，都会第一时间进入这个文件，然后再由这里将事件抛给对应的 App 或 Bsp 层去处理。
    
- **`usart.c / tim.c / adc.c` 等**：具体硬件外设的基础初始化代码（配置波特率、引脚复用、时钟树等）。
    
- **`FreeRTOSConfig.h`**：FreeRTOS 的“总控制面板”。用来配置操作系统的核心参数，比如分配给系统的总堆内存大小、是否开启时间片轮转、看门狗相关配置等。
    

### 5. Drivers 层（官方硬件抽象库）

这里存放的是 ST 官方（意法半导体）和 ARM 官方提供的驱动代码，**在实际工程开发中，我们通常遵循“绝对不修改里面代码”的原则**。

- **`CMSIS/`**：ARM Cortex-M 内核的底层抽象层，包含最核心的寄存器定义和内核汇编指令封装。
    
- **`STM32F4xx_HAL_Driver/`**：大名鼎鼎的 **HAL 库**。它将极其复杂的 STM32 硬件寄存器操作封装成了标准的 C 语言 API 函数。我们前面提到的 `Bsp` 层，本质上就是调用这些 HAL 库函数来干活的。
    

### 6. Middlewares 层（第三方中间件）

顾名思义，这里存放的是非官方但被广泛使用的第三方开源组件。

- **`Third_Party/FreeRTOS/`**：存放着 FreeRTOS 操作系统的完整纯净源码（如 `tasks.c`, `queue.c`, `list.c` 等）以及 CMSIS-RTOS V2 的系统适配层。如果项目后续还要增加网络功能（如 LwIP）或者文件系统（如 FatFS），也会统一放在这里。
    

### 7. MDK-ARM 层（编译工程目录）

- 这是专门为 **Keil MDK**（嵌入式常用的集成开发环境）准备的工程文件夹。里面存放了工程配置文件、编译过程产生的中间文件（`.o`），以及最终烧录到单片机里的 `.hex` 或 `.bin` 固件。

### 💡 整体架构串联总结

现在我们将所有目录拼在一起，整个“烤鸭机器人”下位机的软件执行流转就非常清晰了：

**具体业务逻辑 (`App` 层)** $\rightarrow$ **依赖操作系统调度 (`Middlewares` 层)** $\rightarrow$ **调用自定义驱动封装 (`Bsp` 层)** $\rightarrow$ **调用官方 API 操控硬件 (`Drivers/Core` 层)** $\rightarrow$ **控制底层物理硬件**。

这套分层架构非常经典且规范，极大地提升了代码的**可移植性**和**可维护性**。


# 2、这个项目是做什么的？一段话介绍？

**Kaoya Robot** 是一个面向真实工程交付思路设计的下位机项目，核心目标不是“堆功能”，而是把**分层、可维护、可调试、可扩展**做到位。

你可以把它理解为一个“小型自动驾驶底盘下位机”：
- 上位机下发速度指令（vx / wz）
- 下位机完成协议解析、运动学解算、PID 闭环、PWM 执行
- 同时采集电池电压、编码器速度、IMU 数据
- 通过 Uplink 上报状态，并在 LCD 上实时展示
- MonitorTask 监控系统健康（栈水位、堆、心跳、异常 Hook）
- IWDG 看门狗兜底保证稳定性

# 3、这个项目分了哪些任务？每个任务负责什么？

### 一、 核心业务与控制任务（高优先级）

- **CommTask（通信任务）**
    
    - **优先级**：高优先级（事件驱动）
        
    - **负责什么**：负责**上位机 $\rightarrow$ 下位机**的通信接收与解析（例如解析速度指令 `cmd_vel`）。它通过 UART DMA 接收原始字节流，利用状态机逐字节解析、校验，确保指令有效。
        
    - **设计初衷**：把串口收包和解析的逻辑从运动控制中剥离出来。解析到有效指令后，通过任务通知（Task Notification）告诉 `ControlTask`。这样可以避免控制环路被频繁的通信中断或日志刷屏干扰，保证实时性。
        
- **ControlTask（控制任务）**
    
    - **优先级**：高优先级（事件驱动）
        
    - **负责什么**：负责跑底盘的**运动控制闭环**。包括读取目标速度、进行逆运动学解算（将机器人的线速度/角速度转化为车轮轮速）、运行 PID 算法、输出 PWM 控制电机。
        
    - **设计初衷**：它是机器人的“小脑”，必须保证控制周期的绝对稳定。因此，该任务绝不直接做复杂的 I/O 操作（如串口解析或日志打印），专注于高频的控制计算。
        
- **IwdgTask（看门狗任务）**
    
    - **优先级**：高优先级（固定周期）
        
    - **负责什么**：负责**软件看门狗**的监控。它会周期性地检查系统内各个关键任务的全局心跳变量。
        
    - **设计初衷**：只有当所有关键任务都处于健康状态时，它才会去喂硬件独立看门狗（IWDG）。一旦发现某个关键任务卡死或跑飞，它会果断停止喂狗，触发单片机硬件复位，确保系统具备自恢复能力。
        

---

### 二、 数据采集与上报任务（中优先级）

- **SensorTask（传感器任务）**
    
    - **优先级**：中优先级（固定周期）
        
    - **负责什么**：负责**底层所有硬件传感器的统一采样与单位换算**。包括通过 ADC 获取电池电压、捕获编码器数据（轮速）、以及通过 I2C 读取 IMU（惯性测量单元）的数据。
        
    - **设计初衷**：采集完数据后，它会将结果写入一个全局的“快照（Snapshot）”。其他任务（如上行任务、LCD任务）如果需要数据，直接读取快照即可，不需要直接去操作硬件。这种设计极大地减少了硬件接口的耦合与并发冲突风险。
        
- **UplinkTask（上行任务）**
    
    - **优先级**：中优先级（固定周期）
        
    - **负责什么**：负责**下位机 $\rightarrow$ 上位机**的周期性状态上报（status）。
        
    - **设计初衷**：定期从 `SensorTask` 维护的全局快照中提取最新的传感器数据和系统状态，按照指定的协议帧格式组包，最后通过 USART DMA 稳定地回传给上位机。
        

---

### 三、 系统辅助与人机交互（低优先级）

- **LogTask（日志任务）**
    
    - **优先级**：低优先级（事件驱动）
        
    - **负责什么**：负责**集中式的调试日志输出**（Debug）。
        
    - **设计初衷**：在多任务系统中，如果大家都在各自的任务里直接调用 `printf`，会导致串口数据打架（字符交错乱码）甚至引发阻塞死锁。设计 `LogTask` 后，其他任务只需要把产生的日志扔进缓冲区或队列，由 `LogTask` 统一进行格式化输出和限速处理。
        
- **MonitorTask（监控任务）**
    
    - **优先级**：低优先级（固定周期）
        
    - **负责什么**：充当系统的**健康监控与可观测性中心**。
        
    - **设计初衷**：专门用来统计各个任务的心跳状态、排查堆栈使用率（防止栈溢出）、统计堆内存剩余，并在需要时输出任务列表和诊断信息，是开发阶段调优的利器。
        
- **LcdTask（LCD任务）**
    
    - **优先级**：低优先级（固定周期）
        
    - **负责什么**：负责**人机交互与 UI 界面刷新**。
        
    - **设计初衷**：定期从全局快照中读取当前的电池电量、工作模式或错误码，并在机器人自带的 LCD 屏幕上进行图形化状态展示。

在向面试官介绍时，您可以这样总结这套任务设计的精妙之处：

> “整个系统采用了**前级通信（Comm）事件驱动，核心控制（Control）高频响应，环境感知（Sensor）异步快照，系统状态（Uplink/LCD）周期上报，并辅以独立日志（Log）和软硬件双重监控（Monitor/Iwdg）**的设计架构。
>
